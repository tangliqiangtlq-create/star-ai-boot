# 三方配置位置说明

> 版本：v1.0 | 最后更新：2026-10-11
> 目的：**一张表说清所有第三方服务的配置应该放哪**，避免散落在 yml / env / DB 里找不着。

---

## 一、存储位置总览

三方配置按**生命周期**和**变更频率**分成三层：

```
┌─────────────────────────────────────────────────────────────────────────┐
│ Layer 1 · 基础设施级  ──── env 变量 + Nacos 远程配置                    │
│   DB 起来之前就要用的，不能放 DB                                         │
│   例：MySQL / Redis / RabbitMQ / MinIO endpoint / KMS key              │
└─────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼ DB 启动
┌─────────────────────────────────────────────────────────────────────────┐
│ Layer 2 · 业务级  ──── 业务表 + Redis 缓存 + 变更通知                    │
│   DB 起来后加载，可以运营后台可视化管理                                   │
│   例：AI 厂商凭证 / 支付渠道 AK-SK / KYC API Key                        │
└─────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ Layer 3 · 字典/常量  ──── sys_dict + sys_dict_item                      │
│   通用 KV，非敏感，前端也需要用                                         │
│   例：视频分类枚举 / 订单状态字典 / 国家码                               │
└─────────────────────────────────────────────────────────────────────────┘
```

敏感值加密分层：

| 等级 | 加密方式 | 存放位置 | 例子 |
|------|---------|---------|------|
| **L0 不加密** | 明文 | 全层 | timeout / API base URL / 状态枚举 |
| **L1 应用内加密** | AES-256-GCM-SIV 加密后存密文字段 | Layer 2 DB 业务表 | AI AK/SK / Stripe Secret Key / 支付渠道 private_key |
| **L2 KMS 托管** | KMS Key ID 引用 + 本地 wrap | Layer 1 env | DB 主密码 / Redis 密码 / CloudFront 签名私钥 |
| **L3 环境变量注入** | 启动前由 k8s Secret / .env 注入 | Layer 1 env | 所有 Layer 1 的敏感凭证 |

## 三、加密实现对照

### 3.1 已有加密能力

| 能力 | 实现位置 | 用途 |
|------|---------|------|
| AES-256-GCM-SIV 字段加密 | `star-ai-boot-base-core` · `AesEncryptUtil` | `ai_channel.ak_cipher` / `ai_payment_channel.config_json` 的加密/解密 |
| KMS 环境变量解密 | `star-ai-boot-starter-secrets` · `MpaySecretsEnvironmentPostProcessor` | 启动时把 KMS 里解密的值注入 Spring Environment |
| 华为 KMS | `HuaweiCsmsKmsDecryptor` | 国内云环境 |
| 阿里 KMS | `HttpJsonKmsDecryptor`（HTTP JSON 协议） | 国内云环境 |
| AWS KMS | `AwsKmsDecryptor` | 国际云环境 |
| 本地 AES-GCM | `LocalAesGcmSecretsCrypto` | 开发/测试环境无 KMS |
| 自研 KMS | `MpayKmsDecryptor` | 私有化部署 |
| 敏感字段 Converter | ❌ **未实现** | 让 Jackson / MyBatis-Plus 在读写 `*_cipher` 字段时自动加解密，目前需要业务代码手动调用 `AesEncryptUtil` |

### 3.2 加密调用链（当前 `ai_channel.ak_cipher` 的方式）

```
业务代码创建通道:
  ChannelCreateDTO.ak = "AKLTxxx"          ← 明文字符串
    │
    ▼
aiChannelService.create(dto)
    │  ak_cipher = AesEncryptUtil.encrypt(dto.ak, encryptionKeyRef)
    │  内部: AES-256-GCM-SIV(random_iv, aad="ai_channel.ak", plaintext)
    │         → iv(16B) + tag(16B) + ciphertext(base64)
    │
    ▼
DB 存储 ak_cipher = "4Q+...base64..."       ← 密文

运行时路由选路:
  aiChannelSelector.select(provider, tenantId)
    │  ak = AesEncryptUtil.decrypt(channel.getAkCipher(), channel.getEncryptionKeyRef())
    │  每次都手动 decrypt —— 这是可以接受的（Redis 缓存 layer 2 配置后 decrypt 开销小）
    │
    ▼
HTTP Header: Authorization: Bearer <decrypted_sk>
```

### 3.3 Phase 1 建议：统一 `@Decrypt` 注解 + Converter

```java
// 注解：标记哪些字段需要自动解密
@Target(ElementType.FIELD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Decrypt {
    String keyRef();  // 指向哪个 KMS key / 本地 key
    String aad() default "";  // AES-GCM 的 AAD（绑定表名+列名防串用）
}

// MyBatis-Plus TypeHandler：读 DB 时自动 decrypt，写 DB 时自动 encrypt
public class AesCipherTypeHandler extends BaseTypeHandler<String> { ... }

// Jackson JsonDeserializer：JSON 反序列化时自动 decrypt（用于 Feign 传输）
public class DecryptingJsonDeserializer extends JsonDeserializer<String> { ... }
```

这样业务代码里就不会散落 `AesEncryptUtil.encrypt/decrypt` 调用，全由框架透明处理。
